# База данных бота

Отдельная база в **уже работающем** PostgreSQL, который поднят вместе с
панелью. Новых служб не требуется.

## Какие службы нужны

| | Нужна | Почему |
|---|---|---|
| PostgreSQL | да | уже работает рядом с панелью |
| Valkey / Redis | **нет** | тоже уже работает, но нам не нужен |
| Третий сервер | **нет** | бот живёт рядом с панелью |

**Redis не нужен, хотя он и стоит.** Его берут под кеш, счётчики, очереди
и блокировки между несколькими копиями приложения. У нас одна копия бота и
объём данных, который целиком помещается в памяти сервера; всё
перечисленное PostgreSQL делает сам. Использовать службу только потому,
что она запущена, — значит завести второе место, где данные могут
разойтись с базой, и второй повод для ночного разбора.

Понадобится он в одном случае: когда копий бота станет несколько и им
потребуется общая блокировка, чтобы не обработать одно уведомление дважды.
До этого далеко.

**Бот ставится на машину с панелью** (`nano`, 2 ядра, 4 ГБ). Там уже есть
Docker, PostgreSQL и Caddy с рабочим сертификатом, и там же панель, в
которую бот ходит за ключами, — обращения останутся внутри машины.

На узел (`pico`, 1 ядро, 2 ГБ) ставить нечего: его дело — пропускать
трафик, и всё лишнее на нём отнимает у туннеля и ядро, и память. Хуже
того, это связало бы работу бота с узлом, который однажды заблокируют:
адрес меняется — вместе с ним пропадает приём оплаты.

## Почему отдельная база, а не таблицы рядом с панельными

Панель обновляется своими миграциями и ничего не знает про наши таблицы.
Общая база означает, что её обновление однажды упрётся в наши имена, а наш
`pg_dump` утащит её данные. Разделение стоит одной команды и снимает оба
случая.

Роль тоже отдельная и без прав на чужие базы: ошибка в боте не должна
дотягиваться до данных панели.

## Создать (на сервере с панелью)

Пароль придумайте на месте и **не присылайте его в переписку** — он идёт
только в `.env` бота.

```bash
docker exec -it remnawave-db psql -U postgres <<'SQL'
CREATE ROLE gloria LOGIN PASSWORD 'ПРИДУМАЙТЕ_ЗДЕСЬ';
CREATE DATABASE gloria OWNER gloria;
SQL
```

Имя контейнера уточните по `docker ps` — в разных сборках панели оно
различается.

## Каким адресом к ней подключаться

Создаём базу **изнутри** контейнера, а бот идёт к ней **снаружи**, по TCP.
Эти два конца надо свести, иначе бот скажет `error connecting to server`
при живой и правильно созданной базе.

Панель публикует свой PostgreSQL на хост, но **не на 5432**:

```bash
docker ps --format '{{.Names}}   {{.Ports}}'
# remnawave-db   127.0.0.1:6767->5432/tcp
```

Слева от стрелки — адрес для `GLORIA_DATABASE_URL`, то есть
`127.0.0.1:6767`. Число проверяйте у себя: оно задано в
`docker-compose.yml` панели и в другой сборке может быть другим.

Наружу порт не смотрит — только на `127.0.0.1`. Так и должно быть: бот
живёт на этой же машине, а база, доступная из интернета, — это подарок
любому, кто найдёт пароль в чужом журнале.

## Применить схему

Все миграции по порядку номеров, ни одной не пропуская:

```bash
for m in db/migrations/*.sql; do
  echo "== $m"
  docker exec -i remnawave-db psql -U gloria -d gloria -v ON_ERROR_STOP=1 < "$m"
done
```

Ошибок быть не должно; последняя строка каждой — `COMMIT`.

Уже применённую миграцию второй раз запускать не нужно: она упрётся в
«уже существует». Это не поломка, но и не проверка — учёта применённых
миграций у нас пока нет, и порядок держится на том, что список короткий.

## Проверить сторожа

```bash
docker exec -i remnawave-db psql -U gloria -d gloria -v ON_ERROR_STOP=1 \
  < db/tests/invariants.sql
```

Ожидаемый итог — `NOTICE: все сторожа сработали`. Проверка идёт в
транзакции с откатом: данные не остаются.

Шестнадцать враждебных запросов, каждый обязан упасть: повторная выдача
пробы, сброс отметки о пробе, номер заказа с разделителем, нулевая сумма,
неизвестная валюта, оплата без времени оплаты, повторная доставка того же
уведомления, удаление финансовых записей и прочее.

## Что где лежит

| Файл | Что |
|---|---|
| `migrations/0001_init.sql` | схема целиком |
| `migrations/0002_panel_sync.sql` | очередь согласования даты с панелью |
| `tests/invariants.sql` | проверка того, что ограничения действуют |

Миграции нумеруются и **не переписываются** после того, как применены на
работающей базе: правка уже применённого файла означает, что схема на
сервере и схема в репозитории разошлись, а узнаете вы об этом при
восстановлении из резервной копии.

## Резервная копия

Единственная невосполнимая потеря во всём хозяйстве. Узел переставляется
за час, домен переносится, панель разворачивается заново — а кто сколько
заплатил и до какого числа, не восстановит ничто.

См. `deploy/backup/`.
