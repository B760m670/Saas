# 12 — Точка выхода: порядок запуска

> Приложение установлено, но кнопка «Включить» неактивна. Это правильно:
> ей нечем пользоваться. Здесь — как получить ключ.

---

## 1. Что вообще происходит

Приложение на телефоне — только клиент. Оно умеет разговаривать
протоколом, но не знает, **с кем**. Собеседник — точка выхода:
программа `atlas-exit`, запущенная на машине, у которой доступ в
интернет не ограничен.

```text
телефон ──REALITY+VLESS──► atlas-exit ──обычным образом──► интернет
   (в ограниченной сети)     (там, где не ограничен)
```

Ключ `vless://…` — это визитка точки выхода: адрес, кому стучаться,
чем шифровать, каким сайтом прикидываться. Печатает её сама
`atlas-exit` при запуске.

Арендованных серверов в проекте нет по замыслу — значит, точку выхода
запускает сам пользователь там, где у него есть машина.

---

## 2. Что нужно от машины

Ровно одно требование, и оно жёсткое:

> **До этой машины должен доходить входящий TCP-connect с телефона.**

Это не одно и то же, что «на машине есть интернет». Интернет есть у
всех, а входящие соединения принимает далеко не всякая машина.

| Где машина | Обычно работает? |
|---|---|
| Обычный домашний интернет с «белым» IPv4 | да, после проброса порта на маршрутизаторе |
| Домашний интернет с «серым» IPv4 (CGNAT, адрес вида `100.64.…`) | **нет**, см. §6 |
| Мобильный интернет | почти никогда |
| Любой сервер с публичным адресом | да |
| Другая машина в той же сети Wi-Fi | да, но только пока телефон в этой же сети |

Последняя строка — самый быстрый способ **проверить, что всё
собранное вообще работает**, не решая пока задачу с внешним адресом.
С неё и стоит начать.

| `atlas-exit-windows-x86_64.zip` | Windows |


Подписи у файлов нет. Windows и macOS будут ругаться на неизвестного

## 4. Пробный запуск: телефон и машина в одной сети Wi-Fi

Узнать адрес машины в локальной сети:

```bash
ip -4 addr show          # Linux
ipconfig getifaddr en0   # macOS
ipconfig                 # Windows, строка IPv4-адрес
```

Пусть это `192.168.1.50`. Запуск:

```bash
./atlas-exit --listen 0.0.0.0:8443 --host 192.168.1.50:8443 \
             --cover www.microsoft.com:443
```

Напечатается такое:

```text
слушает          0.0.0.0:8443
адрес для ключа  192.168.1.50:8443 — адрес частный: ключ сработает
                 только с устройств этой же локальной сети. Из интернета — нет
сайт прикрытия   www.microsoft.com:443
публичный ключ   AsFwpLFoHwyM4GP-qVHxv5hT3teSj4T4RQgvsjowrWI

Ключ доступа (вставить в клиент):
vless://36a7ac6b-…@192.168.1.50:8443?type=tcp&security=reality&…#atlas
```

Ключ целиком — в поле «Ключ доступа» приложения. Телефон должен быть в
той же сети Wi-Fi. Дальше: «Включить» → «Открыть браузер».

Если страница открылась — работает вся цепочка: TLS, REALITY, VLESS,
прокси на телефоне, браузер. Осталось только вынести точку выхода
туда, где до неё дотянутся снаружи.

### Про `--listen` и `--host`

Это **разные адреса**, и путать их — самая частая ошибка.

- `--listen` — где занять сокет на этой машине. `0.0.0.0` значит «на
  всех сетевых картах».
- `--host` — по какому адресу до машины достучится телефон. Именно он
  попадает в ключ.

Раньше в ключ подставлялся адрес прослушивания, и при `--listen
0.0.0.0` получалась ссылка на `0.0.0.0` — заведомо мёртвая, но с виду
настоящая. Теперь без `--host` при `0.0.0.0` программа отказывается
стартовать: лучше внятный отказ сразу, чем поиск причины в туннеле.

## 5. Наружу: белый IPv4

Узнать, какой адрес видит интернет:

```bash
curl -4 https://ifconfig.me
```

Если он совпадает с адресом на WAN-интерфейсе маршрутизатора — адрес
белый. Тогда:

1. **Проброс порта.** В настройках маршрутизатора: внешний порт `443` →
   внутренний адрес машины, порт `8443`. Раздел называется
   «Port Forwarding», «Виртуальный сервер» или «NAT».
2. **Брандмауэр** на самой машине должен пропускать входящие на `8443`.
3. Запуск:

   ```bash
   ./atlas-exit --listen 0.0.0.0:8443 --host 203.0.113.7:443 \
                --cover www.microsoft.com:443
   ```

   Порт в `--host` — внешний (`443`), в `--listen` — внутренний
   (`8443`). Программа это различает.

4. **Проверить снаружи**, а не изнутри своей же сети: многие
   маршрутизаторы не заворачивают собственный внешний адрес обратно
   внутрь, и проверка с домашнего ноутбука соврёт. Проще всего — с
   телефона, выключив Wi-Fi:

   ```
   443-й порт на 203.0.113.7 должен принимать соединение
   ```

Почему именно `443` наружу: на этом порту живёт весь HTTPS, и
соединение к нему ничем не выделяется. Нестандартный порт сам по себе
приметен.

---

## 6. Если адрес серый (CGNAT)

Признак: `curl -4 https://ifconfig.me` показывает одно, а на
маршрутизаторе стоит адрес из `100.64.0.0/10`, `10.0.0.0/8` или
`192.168.0.0/16`. Значит, провайдер прячет за одним адресом многих
абонентов, и входящее соединение до вас не дойдёт — пробрасывать
нечего.

Честный список того, что тут можно сделать:

1. **IPv6.** Самый недооценённый вариант. Многие провайдеры, в том
   числе мобильные, выдают **публичный** IPv6 даже там, где IPv4
   серый. Проверить:

   ```bash
   curl -6 https://ifconfig.me
   ```

   Если ответ есть и он не начинается с `fd`/`fe80` — адрес публичный,
   и его можно ставить в `--host`. Оговорка: телефон должен быть в
   сети с IPv6, иначе он до этого адреса не доберётся. У мобильных
   операторов IPv6 распространён.

2. **Белый IPv4 у провайдера.** Обычно услуга существует и стоит
   символических денег. Это единственный пункт списка, где деньги
   всё-таки появляются, — и решает его пользователь, а не проект.

3. **Машина в другом месте.** Рабочий компьютер, машина у знакомого,
   бесплатный тариф у облачного провайдера. Требование то же:
   публичный адрес и открытый порт.

Чего здесь **нет** и не будет обещано: способа принять входящее
соединение на машину за CGNAT без посредника. Такого способа не
существует — посредник нужен всегда, вопрос лишь в том, кто им будет.
Ярус ретрансляторов описан в `docs/03-infrastructure.md`; в коде его
пока нет.

---

## 7. Постоянный ключ

По умолчанию при каждом запуске ключи новые — старая ссылка перестаёт
работать. Так задумано: точка выхода одноразовая, и утечка ключа не
компрометирует прошлые сеансы.

Чтобы ссылка пережила перезапуск, задайте секрет явно:

```bash
./atlas-exit --secret ВАШ_СЕКРЕТ_BASE64URL --uuid ВАШ_UUID --sid dead …
```

Секрет — 32 байта в base64url без выравнивания. Хранить его надо как
пароль: кто им владеет, тот выдаёт себя за вашу точку выхода.

---

## 8. Чего эта страница не утверждает

Что описанное проверено на живом железе. Проверено следующее:

- сборка запускается и печатает ключ (шаг «Проверить, что запускается»
  в `release.yml`, на всех трёх системах);
- отказ при `0.0.0.0` без `--host` действительно отказ, а не мёртвый
  ключ (там же, и тесты в `atlas-exit/src/link.rs`);
- цепочка «клиент → точка выхода → цель» проходит целиком в тестах
  `atlas-exit/tests/end_to_end.rs`, но на петле, а не через настоящую
  сеть.

Проброс порта, CGNAT и IPv6 из §5–6 — это описание того, как устроены
сети, а не отчёт о проведённом опыте. Первый настоящий прогон «телефон
в ограниченной сети → точка выхода снаружи» ещё не сделан; когда
будет — попадёт в `docs/10-field-data.md`.
