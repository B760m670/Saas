## 1. Кто противник

| Уровень | Актор | Возможности | Что видит |
|---|---|---|---|
| L1 | Оператор связи (МТС, МегаФон, Билайн, Tele2, Ростелеком) | Маршрутизация, NAT, шейпинг, логи NetFlow | IP:порт, объём, тайминги |
| L2 | **ТСПУ** (техсредства противодействия угрозам, ставятся ЦМУ ССОП в разрыв сети оператора) | DPI в реальном времени на всём трафике, активное вмешательство: RST, дроп, throttling, подмена DNS, **активное зондирование** | SNI/ECH, JA3/JA4, размеры и тайминги пакетов, энтропия, поведение потока |
| L3 | Центральный координатор (РКН/ЦМУ ССОП) | Глобальная корреляция между операторами, реестры, «белые списки», региональные шатдауны | Агрегированную статистику по всем L2 |
| L4 | Оператор платформы (Apple, Google, GitHub, Cloudflare) | Удаление приложения, отзыв аккаунта, блокировка Worker'а | Метаданные аккаунта, содержимое деплоя |

**Ключевой вывод:** противник — не пассивный фильтр. Он *активен* (шлёт свои пробы к твоему серверу, чтобы проверить, VPN ли это) и *статистический* (не ищет сигнатуру, а строит вероятностную модель «это похоже на прокси»).

## 2. Арсенал противника — конкретные техники

### 2.1 SNI-фильтрация и ECH
Базовый уровень. ТСПУ читает `server_name` в ClientHello и режет по списку.
Ответ индустрии — **ECH (Encrypted Client Hello)**. Ответ ТСПУ — **блокировка самого факта ECH**: с осени 2024 трафик с ECH-расширением к Cloudflare режется. То есть «включить ECH» — это *ухудшить* маскировку в РФ, потому что ECH там сам по себе аномалия.

**Следствие для нас:** ECH — не решение. Нужна маскировка, которая выглядит как *самый обычный* TLS без экзотических расширений.

### 2.2 Fingerprinting TLS (JA3 / JA4 / JA4+)
Хэш от набора и порядка cipher suites, расширений, эллиптических кривых, ALPN. Библиотеки Go/Rust имеют TLS-отпечаток, отличный от Chrome/Firefox. Голый Go-стек в ClientHello = мгновенный флаг.

**Следствие:** обязателен **uTLS** (или Rust-аналог) с имитацией актуального отпечатка Chrome, ротацией и согласованием с User-Agent, если он есть.

### 2.3 Активное зондирование (active probing)
Классика GFW, перенятая ТСПУ. Логика: заметили подозрительный поток на `1.2.3.4:443` → через N минут сами подключаются на этот адрес и шлют мусор/полуоткрытый TLS. Если сервер отвечает не как настоящий веб-сервер (закрывает соединение, возвращает нестандартную ошибку, не имеет валидного сертификата) → адрес в бан.

**Это убивает** классические VMess/Shadowsocks/Trojan на голом VPS.
**Это НЕ убивает REALITY** — потому что REALITY при неавторизованном подключении прозрачно проксирует пробу на *настоящий* чужой сайт, и пробующий получает настоящий сертификат настоящего google.com. Отличить невозможно.

### 2.4 Статистический анализ потока
Без расшифровки: распределение размеров пакетов, межпакетные интервалы, соотношение up/down, длительность сессий, энтропия первых байт.

- Shadowsocks без плагина = поток с равномерно случайными первыми байтами → «нет никакого протокола» → аномалия.
- WireGuard = фиксированный хэндшейк 148/92 байта и `type` байт в начале → сигнатура тривиальна, блокируется по одному пакету.
- QUIC-прокси = легко отличить от браузерного QUIC по паттерну congestion control.

**Следствие:** нужен слой **padding/timing-обфускации** и congestion control, имитирующий браузер, а не «залить канал».

### 2.5 Тротлинг вместо блокировки
Самая коварная тактика. Соединение не рвётся — ему просто режут скорость до 100–200 Кбит/с. Пользователь думает «VPN сломался», а фактически ТСПУ понизил приоритет. Так душили YouTube.

**Следствие:** клиент обязан **измерять** качество, а не только факт коннекта, и уметь мигрировать при деградации.

### 2.6 Блокировка по IP и ASN
Массовые баны диапазонов известных хостеров (DigitalOcean, Hetzner, Vultr, OVH, Amazon Lightsail). Дата-центровый ASN — сам по себе фактор риска.

**Следствие:** предпочтительны IP, которые дорого банить: CDN-диапазоны (Cloudflare, Fastly), residential-адреса волонтёров, IP крупных PaaS, смешанные с легитимным трафиком.

### 2.7 «Белый список» и региональные шатдауны
Отдельная, более жёсткая модель угрозы: в ряде регионов мобильный интернет отключается полностью, кроме перечня Минцифры (>500 российских сервисов на май 2026: госуслуги, банки, маркетплейсы, такси, СМИ).

Это **инверсия** обычной задачи. Тут не «обойти чёрный список», а «работать, когда разрешён только whitelist». Обычный VPN тут бесполезен: пакеты до иностранного IP просто не выходят.

**Следствие:** нужен отдельный режим — туннелирование *внутри* разрешённого трафика (см. `03-infrastructure.md`, раздел «Режим белого списка»). Это самая сложная и самая ценная часть проекта.

### 2.8 Блокировка отдельных приложений
Отдельно душат конкретные сервисы (мессенджеры, видеохостинги) при живом интернете в целом. Часто — по IP+SNI+QUIC одновременно.

**Следствие:** нужен per-app / per-domain routing, чтобы гнать через туннель только страдающий трафик, а остальное — напрямую. Это и быстрее, и *менее заметно* (меньше объёма в туннеле = меньше внимания).

## 3. Наша модель безопасности

### 3.1 Что мы защищаем
1. **Доступность** — пользователь получает работающий интернет. Приоритет №1.
2. **Неразличимость (undetectability)** — сам факт использования обхода не должен быть виден оператору. Приоритет №2.
3. **Конфиденциальность содержимого** — от оператора и от промежуточных релеев.
4. **Неотслеживаемость пользователя** — мы сами не должны иметь логов, связывающих личность с трафиком.

### 3.2 Явные цели (goals)
- G1. Трафик клиента статистически неотличим от обычного HTTPS/QUIC к популярным сайтам.
- G2. Активное зондирование любого нашего endpoint'а даёт ответ настоящего постороннего сайта.
- G3. Компрометация одного релея не раскрывает остальные и не деанонимизирует пользователей.
- G4. Противник, получивший клиент и создавший 1000 аккаунтов, **не** может перечислить все endpoint'ы сети (anti-enumeration).
- G5. Нулевая денежная стоимость инфраструктуры для проекта и для пользователя.
- G6. Отсутствие единой точки отказа в control plane.

### 3.3 Явные не-цели (non-goals) — честно
- **Не** защита от глобального пассивного наблюдателя, коррелирующего трафик на входе и выходе (это Tor-задача, и Tor её решает лишь частично). Наш противник — национальный, не глобальный.
- **Не** анонимность уровня Tor. Мы даём обход цензуры и приватность от провайдера, но exit-релей волонтёра видит назначения. Это должно быть честно написано в UI.
- **Не** обход блокировок при *полном* физическом отключении сети (нет канала — нет обхода; mesh/Bluetooth — отдельная задача вне первого этапа).
- **Не** защита скомпрометированного устройства.

### 3.4 Риски, которые мы принимаем сознательно
| Риск | Митигация |
|---|---|
| Volunteer exit видит незашифрованный DNS/SNI | Форсируем DoH/DoT внутри туннеля + предупреждение в UI + приоритет доверенных релеев для чувствительного трафика |
| Sybil-атака: противник поднимает свои релеи и логирует | Репутация + мульти-хоп для чувствительного профиля + подписанные дескрипторы |
| Enumeration: противник выкачивает все адреса | Lox-подобная выдача по анонимным credential'ам (см. `04-control-plane.md`) |
| Бан аккаунта на PaaS/CDN за прокси | Каждый пользователь — на своём аккаунте; бан одного не задевает других |
| Отзыв iOS-сертификата | Множественные каналы дистрибуции, self-hosted source JSON |

## 4. Правовой контекст — фактически

В РФ действует запрет на распространение информации о способах обхода блокировок и ограничения на работу VPN-сервисов; с 2024 года усилена ответственность за рекламу и распространение таких средств. Разработка и использование ПО для обхода цензуры — вопрос, который каждый участник решает для себя сам, с учётом своей юрисдикции.

Практические следствия для проекта, независимо от правовой оценки:
- Проект ведётся публично на GitHub — юрисдикция США, инструменты обхода цензуры там легальны и широко распространены (Tor, Xray, sing-box).
- Никакой централизованной коммерции, платежей, персональных данных — нечего изымать и нечего блокировать по финансовому следу.
- Zero-knowledge по дизайну: у проекта физически нет базы пользователей.

## 5. Что из этого следует для архитектуры — короткий список

1. Базовый транспорт — **VLESS + REALITY** (единственный, устойчивый к активному зондированию).
2. Обязателен **uTLS**-отпечаток реального браузера.
3. Обязателен **полиморфизм**: несколько транспортов + автопереключение по измерениям, а не по факту «коннект/не коннект».
4. Нужен **режим без сервера вообще** (DPI-десинхронизация) — он решает задачу «заблокирован конкретный сайт» с нулевой инфраструктурой и нулевой заметностью.
5. Нужен **режим белого списка** — туннель внутри разрешённого трафика.
6. Инфраструктура — **распределённая по бесплатным аккаунтам самих пользователей**, а не централизованная.
7. Раздача endpoint'ов — **криптографическая, устойчивая к перечислению**, а не «ссылка в телеграм-канале».
