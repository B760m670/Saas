# 03 — Инфраструктура без аренды серверов

> **Этот документ описывает путь, который проверен и не сработал.**
> Оставлен как запись рассуждения и как предостережение — не как план.

---

## 0. Чем всё кончилось

Замысел был: бесплатные площадки вместо арендованных машин, и первым
ярусом — Cloudflare Workers. Край был написан, развёрнут и **работал**:
ключ давал 19,8 МБ/с и открывал YouTube с Instagram.

Потом перестал. Разбор по шагам — в `docs/10-field-data.md`; коротко:

**У оператора недоступна вся сеть Cloudflare целиком.** Не наш адрес, не
наш Worker — вся площадка. Это подтверждается и сторонним измерением: в
списке полностью ограниченных автономных систем (391 AS, свыше 225 млн
адресов) лежат Cloudflare, Hetzner, DigitalOcean, Amazon, Vultr, Contabo,
Scaleway, Linode и другие.

Отсюда вывод, ради которого документ и сохранён:

> **Бесплатная площадка блокируется целиком и сразу для всех её
> пользователей. Дешевизна адреса и есть причина, по которой его дёшево
> заблокировать: он общий.**

Ярусы, опиравшиеся на чужие бесплатные площадки, из плана убраны.
Код края на Cloudflare удалён вместе с крейтом `atlas-transport`,
который существовал только ради разговора с ним; при надобности всё
достаётся из истории.

Работающий путь — арендованный узел со своим адресом, и он описан в
`docs/13-vps.md`.

## 1. Сначала — честная физика

Обойти это невозможно, и делать вид, что можно, — значит построить нерабочий продукт:

> **Чтобы получить контент, заблокированный для твоего IP, нужен какой-то узел с незаблокированным IP, который его получит и передаст тебе. Точка выхода существует всегда.**

Отсюда вопрос ставится правильно не как «как обойтись без узлов», а как:

> **Как получить точки выхода, за которые никто не платит деньгами и которые невозможно перечислить и забанить оптом?**

Ответ проекта — **шесть независимых ярусов**, каждый со своей экономикой и своим профилем блокируемости. Ни один не является единственной точкой отказа.

---

## 2. Ярус T0 — вообще без точки выхода

**DPI-десинхронизация.** Ноль инфраструктуры, ноль третьих лиц, ноль трафика через посредников. Трафик идёт напрямую к настоящему сайту — просто ТСПУ не может его разобрать.

Техники:
| Приём | Механика |
|---|---|
| Фрагментация TLS record | ClientHello режется так, что SNI попадает на границу сегментов; DPI без реассемблинга его не видит |
| TCP-сегментация с рассинхроном | Отправка не по порядку / с перекрытием — DPI и сервер собирают разное |
| Fake-пакеты | Перед настоящим ClientHello шлётся поддельный с малым **TTL** (умрёт до сервера, но DPI его увидит и запомнит «безобидный» SNI) или с битой контрольной суммой (сервер отбросит, DPI — нет) |
| `--wssize` / манипуляции окном | Сервер вынужден дробить ответ, ломая сигнатуру |
| Desync для QUIC | Аналогично, по Initial-пакету |

**Покрытие:** решает «не открывается конкретный сайт» — то есть большую часть реальных жалоб пользователей в РФ. **Не решает** гео-ограничения на стороне сервиса и полный блок по IP.

**Реализация по платформам:**
- Windows: WinDivert (как GoodbyeDPI) — работает системно.
- Linux: nfqueue + nftables (как zapret) — системно.
- Android: локальный SOCKS5/VpnService без внешнего сервера (как ByeDPI) — трафик остаётся на устройстве.
- macOS: NE + pf.
- iOS: **только** через локальный прокси / NE, трафик наружу идёт напрямую.

Это должен быть **режим по умолчанию** — самый быстрый, самый незаметный, ничего не стоит.

## 3. Ярус T1 — Serverless edge (бесплатные квоты)

Крайне ценный ярус: IP принадлежат крупным CDN, забанить их = положить пол-интернета.

| Платформа | Бесплатная квота | Транспорт | Особенности |
|---|---|---|---|
| **Cloudflare Workers** | 100 000 запросов/сутки | VLESS over WebSocket / XHTTP | `connect()` из Worker; нельзя коннектиться на CF-адреса → нужен `proxyIP` |
| **Cloudflare Pages** | безлимит запросов на static + функции | то же | обходит суточный лимит Workers |
| **Deno Deploy** | 1 млн запросов/мес, 20 ГБ egress | WebSocket | TypeScript, холодный старт ~мс |
| **Vercel / Netlify** | функции с лимитом времени | HTTP-транспорт | плохо для долгих соединений |
| **Val Town** | небольшая квота | WebSocket | быстрый прототип |

**Ограничения, о которых надо знать сразу:**
- Нет UDP → нет QUIC/Hysteria2/WireGuard. Только TCP-протоколы.
- Cloudflare Workers не могут открыть соединение на IP самой Cloudflare → сайты за CF требуют промежуточного `proxyIP`.
- Долгоживущие WebSocket-соединения расходуют CPU-время квоты.
- Массовое использование одного и того же `pages.dev`-поддомена = сигнатура.

**Как обходим:** у каждого пользователя **свой** Worker в **своём** аккаунте на **своём** поддомене. Квота 100 тыс. запросов/сутки на одного человека — это с запасом. См. раздел 7.

## 4. Ярус T2 — Free-tier PaaS с контейнерами

Здесь уже можно запустить полноценный Xray/sing-box с REALITY.

| Платформа | Что даёт | Пригодность |
|---|---|---|
| **Hugging Face Spaces** | Docker, ~7 ГБ RAM, публичный URL, бессрочно | очень хорошо; порт 7860, WS работает |
| **Koyeb** | 1 инстанс бесплатно, свой домен | хорошо |
| **Render** | web service, засыпает при простое | средне (холодный старт) |
| **Fly.io** | бесплатный allowance | хорошо, есть UDP |
| **Railway / Zeabur / Northflank** | триальные квоты | средне |
| **Google Cloud Run** | 2 млн запросов/мес бесплатно | хорошо, но нужен billing-аккаунт |

**Плюс:** полноценный процесс, можно REALITY, можно UDP (у некоторых).
**Минус:** платформы борются с прокси в ToS; аккаунт могут закрыть. Поэтому — снова: аккаунт **пользователя**, не проекта.

## 5. Ярус T3 — Always-free виртуальные машины

Полноценный VPS, бесплатно и бессрочно, но требует регистрации с картой.

| Провайдер | Что | Нюанс |
|---|---|---|
| **Oracle Cloud Always Free** | до 4 ядер ARM Ampere + 24 ГБ RAM + 200 ГБ диска, 10 ТБ трафика/мес | лучшее, что есть бесплатно; часто «нет ёмкости» в популярных регионах, нужен скрипт-перехватчик |
| **Google Cloud** | e2-micro в отдельных регионах US | 1 ГБ egress/мес — мало |
| **AWS / Azure** | 12 месяцев | не бессрочно |

Это **самый качественный** ярус: свой IP, свой REALITY, полный контроль, ~10 ТБ/мес. ATLAS должен уметь **развернуть это в один клик** — от создания инстанса до готового ключа.

Риск: ASN Oracle известен и частично банится. Митигация — REALITY + ротация + смешивание с другими ярусами.

## 6. Ярус T4 — Волонтёрский P2P-mesh (сердце проекта)

Здесь проект перестаёт зависеть от чьей-либо доброй воли, кроме воли пользователей.

### 6.1 Модель Snowflake, адаптированная
- Пользователь ATLAS **в свободной стране** включает в приложении тумблер «Помогать другим».
- Его устройство становится эфемерным WebRTC-прокси.
- Пользователь в РФ через брокер получает ICE-кандидатов и поднимает **DataChannel**.
- Трафик снаружи выглядит как **видеозвонок**: DTLS-SRTP поверх UDP со STUN-обменом. Это не «неизвестный UDP-протокол», это самый массовый паттерн потребительского интернета.

### 6.2 Почему это неблокируемо
1. Адреса — **residential**, домашние IP тысяч людей. Забанить = забанить абонентов.
2. Пул **постоянно меняется** — прокси живёт минуты. Перечислить бессмысленно.
3. ~~Блокировать WebRTC целиком = сломать Zoom, Teams, Discord, Google Meet.~~ **Довод опровергнут измерениями** (см. `10-field-data.md`, раздел 4): `meet.google.com` даёт 75.8 % аномалий, `discord.com` — 59.4 %. Их сломали. Устойчивость T4 держится не на нежелании противника ломать массовые сервисы, а на том, что пул адресов постоянно меняется и не поддаётся перечислению.
4. Для рандеву не нужен наш сервер — используются публичные STUN и распределённый брокер.

### 6.3 Наши расширения над классическим Snowflake
| Проблема Snowflake | Наше решение |
|---|---|
| Медленно, качество непредсказуемо | **Мультипуть**: одновременно 3–5 «снежинок», трафик распределяется по производительности (взвешенный round-robin с обратной связью) |
| Волонтёров мало, нет стимула | Репутация + «карма»: чем больше отдал, тем выше приоритет доступа в дефиците (см. `04-control-plane.md`) |
| Брокер централизован → блокируется | Брокер распределён: DHT + N резервных каналов рандеву (DoH TXT, Nostr, WebSocket-релеи) |
| Часть серверов STUN заблокирована | Блокировка точечная: по измерениям, часть серверов даёт 1–4 % отказов, часть — 98 %. Клиент проверяет и выбирает живые, список пополняется краудсорсингом. **UDP на порту 443 не использовать** — тот же сервер на 3478 проходит, на 443 нет |
| Волонтёр видит трафик | Обязательное сквозное шифрование до T1/T3-узла: волонтёр — **транспорт**, а не exit. Он видит только шифртекст |

### 6.4 Важная архитектурная деталь: волонтёр ≠ выход
Волонтёр WebRTC — это **первый хоп**, а не точка выхода. Схема:

```
Клиент(РФ) ──WebRTC(похоже на звонок)──▶ Волонтёр ──обычный HTTPS──▶ Relay(T1/T3) ──▶ Интернет
             └───────── зашифровано сквозняком до Relay ──────────┘
```

Так волонтёр:
- не несёт правовой ответственности за содержание чужого трафика (он видит только шифртекст, exit-нода не он);
- не может логировать назначения;
- не подставляет свой домашний IP под abuse-жалобы.

Это принципиальное отличие от «дай другу свой Wi-Fi».

## 7. Ярус T5 и главная идея: **каждый пользователь — сам себе оператор**

### 7.1 Суть
Классический бесплатный VPN умирает от арифметики: 100 000 пользователей на инфраструктуре одного энтузиаста = либо деньги, либо смерть.

ATLAS переворачивает это:

> **Приложение автоматически разворачивает точку выхода на бесплатном аккаунте самого пользователя.**

Пользователь один раз проходит мастер: «Создать свою точку» → авторизация в Cloudflare (или Oracle/HF) → приложение само:
1. создаёт Worker/контейнер/инстанс;
2. генерирует X25519-пару для REALITY;
3. подбирает подходящий `dest` из проверенного списка;
4. заливает конфиг;
5. получает готовую точку и добавляет её в свой профиль;
6. **опционально** публикует дескриптор в общий каталог — и его точка начинает помогать другим, а он получает карму.

### 7.2 Почему это меняет всё

| Свойство | Централизованный бесплатный VPN | ATLAS |
|---|---|---|
| Стоимость на пользователя | растёт линейно | **0** |
| Точек выхода | десятки | **столько, сколько пользователей** |
| Перечислимость противником | тривиальна | практически невозможна |
| Эффект бана | все пользователи | один пользователь |
| Масштабирование | упирается в бюджет | **растёт с числом пользователей** |

Это система с **отрицательной стоимостью масштабирования по устойчивости**: чем больше пользователей, тем труднее её блокировать. Именно этого не может ни один коммерческий VPN.

### 7.3 Что нужно реализовать (`core/atlas-provision/`)
- Провайдеры: Cloudflare (Workers/Pages), Hugging Face, Koyeb, Fly.io, Oracle OCI, Deno Deploy.
- Единый trait `Provisioner`: `create() / status() / rotate() / destroy()`.
- Хранение токенов доступа — **только на устройстве**, в Keychain / Keystore / DPAPI / Secret Service. Никогда не уходят с устройства.
- Автообновление: ротация UUID и `dest` раз в N дней без участия пользователя.
- Аварийное уничтожение (panic destroy).

## 8. Особый режим: **белый список**

Самый сложный сценарий. Мобильный интернет отключён, разрешён только перечень Минцифры (>500 сервисов: госуслуги, банки, маркетплейсы, такси, СМИ).

Обычный VPN тут не работает вообще: пакеты до иностранного IP не выходят из сети оператора.

### 8.1 Что теоретически возможно
Здесь честность обязательна: **гарантированного решения нет**, и любой, кто обещает его, врёт. Но есть направления с реальным шансом, ранжированные по перспективности:

| Вектор | Идея | Оценка |
|---|---|---|
| **Разрешённый CDN как носитель** | Часть whitelist-сервисов раздаётся через CDN, которые обслуживают и другие домены. Если разрешение сделано по IP/подсети — то же соединение можно использовать для другого хоста за тем же CDN (классический domain fronting, вернувшийся из-за грубости фильтра) | наиболее перспективно; требует непрерывного картирования, что именно разрешено на каждом операторе |
| **DNS-канал** | DNS часто остаётся рабочим даже при whitelist. Туннель в DoH/DoT/обычный DNS. Медленно (десятки Кбит/с), но хватает для текста и координации | реалистично как «спасательный канал», не как интернет |
| **STUN/TURN разрешённых мессенджеров** | Если разрешён мессенджер со звонками — разрешён и его WebRTC-обмен. Возможность вклиниться в тот же STUN-путь | требует исследования, зависит от реализации фильтра |
| **Соседский bridge** | Устройство с работающим проводным интернетом раздаёт доступ по локальной сети/Wi-Fi Direct/BLE соседям с мобильными | работает надёжно, но требует физического соседства |
| **Оффлайн-mesh** | Bluetooth/Wi-Fi Aware для передачи сообщений при полном шатдауне | вне рамок VPN, отдельный модуль |

### 8.2 Что делаем в проекте
1. Модуль **WhitelistProbe** — автоматически выясняет на конкретном операторе, *как именно* реализован whitelist (по IP? по SNI? по DNS?). Это ключевое знание, и оно разное у разных операторов и регионов.
2. Модуль **CDN-mapper** — строит карту «разрешённый домен → CDN → какие ещё домены за ним».
3. **DoH-туннель** как гарантированный минимальный канал (для получения свежих ключей и координации, даже если полноценный туннель невозможен).
4. Краудсорсинг наблюдений: клиенты анонимно сообщают, что работало, а что нет, в каком регионе/операторе. Это ценнейший датасет, которого нет ни у кого.

## 9. Чего мы НЕ делаем — и почему

| Соблазн | Почему нет |
|---|---|
| **GitHub Actions как прокси-релей** | Прямое нарушение ToS GitHub (запрет на проксирование и нецелевое использование раннеров). Итог — бан аккаунта, а вместе с ним и всей сборки, и дистрибуции. **Actions используем строго для сборки.** |
| Бесплатные триалы по краденым/виртуальным картам | Мошенничество |
| Ботнет / чужие устройства без согласия | Абсолютно исключено. Волонтёрство — только явное, с чётким объяснением рисков и с тумблером выключения |
| Скрытая раздача чужого канала | Тумблер «помогать» **выключен по умолчанию**, включается осознанно, с экраном-объяснением |
| Майнинг/монетизация трафика пользователей | Разрушает доверие, которое и есть весь капитал такого проекта |
