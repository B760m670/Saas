# 05 — Клиенты по платформам

## 1. iOS — начинаем отсюда, и здесь есть проблема

### 1.1 Как вообще устроен VPN на iOS

Есть ровно три способа увести трафик приложения/системы:

| Способ | Что нужно | Custom-протокол |
|---|---|---|
| **Personal VPN** (`NEVPNManager`) | entitlement `com.apple.developer.networking.vpn.api` | ❌ только встроенные IKEv2/IPsec |
| **Packet Tunnel Provider** (`NEPacketTunnelProvider`) | entitlement `com.apple.developer.networking.networkextension` + **отдельный таргет app extension** | ✅ любой |
| **Локальный прокси в самом приложении** | ничего | ✅, но только свой трафик или трафик через системную настройку прокси |

Для VLESS/REALITY нужен **Packet Tunnel Provider**. Это не библиотека внутри приложения — это **отдельный процесс-расширение**, который система запускает по своим правилам, регистрируя его через установленный бандл.

### 1.2 LiveContainer: что он может и чего не может

LiveContainer запускает **любые обычные приложения** — тут никаких ограничений нет. Ограничение ровно одно, и оно касается конкретно расширений. Цитата из README самого проекта, раздел Limitations:

> «**App extensions aren't supported.** they cannot be registered because: LiveContainer is sandboxed, SpringBoard doesn't know what apps are installed in LiveContainer, and they take up App ID.»
>
> «Entitlements from the guest app are not applied to the host app.»

Почему это бьёт именно по VPN: `NEPacketTunnelProvider` **не является частью приложения**. По архитектуре Apple это отдельный процесс, который порождает система (`SpringBoard`/`pkd`) по записи в базе установленных приложений. Гостевые приложения LiveContainer в этой базе отсутствуют — они живут внутри процесса хоста. Система физически не знает, что нужно запускать. Это следствие модели процессов iOS, а не недоработка LiveContainer.

**Практический вывод:** под LiveContainer работает всё, кроме системного туннеля. Значит трафик надо забирать другим способом — и он есть, причём полноценный.

### 1.3 Три пути

#### Путь A. **LiveContainer-совместимая сборка: локальный прокси** (работает у всех, бесплатно, на самых свежих iOS)

Приложение внутри себя поднимает ядро с локальным inbound `127.0.0.1:1080` (SOCKS5) и `127.0.0.1:1087` (HTTP). Дальше:

- **Wi-Fi**: в настройках сети вручную (или через `.mobileconfig`-профиль, который приложение сгенерирует) прописывается HTTP-прокси `127.0.0.1:1087`. **Весь системный трафик, уважающий прокси, идёт через ядро.** Это Safari и подавляющее большинство приложений на `URLSession`.
- **PAC-файл**: iOS нативно поддерживает Proxy Auto-Config — можно раздавать правила маршрутизации (что напрямую, что через туннель) без всякого VPN.
- **Встроенный браузер** в приложении — гарантированно работает через ядро, без каких-либо системных настроек.

Ограничения — честно:
- ❌ **Не работает на мобильном интернете** (в настройках сотовой сети нет поля прокси без supervised-профиля).
- ❌ Не покрывает приложения, игнорирующие системный прокси, и не покрывает UDP/QUIC (частично лечится запретом QUIC в PAC).
- ✅ Зато **не нужен ни платный аккаунт, ни особые entitlements** — работает ровно в той схеме, что у тебя уже есть.

#### Путь B. **TrollStore** (бесплатно, но только на уязвимых версиях iOS)

TrollStore подписывает IPA с **произвольными entitlements**, включая `networkextension`, постоянно и без 7-дневного истечения. Работает на iOS 14.0–16.6.1 и 17.0 (зависит от устройства/эксплойта). На современных iOS 17.1+ — нет.

Если целевая аудитория сидит на старых прошивках — это полноценный бесплатный VPN. Собираем **тот же** IPA, что и для пути C.

#### Путь C. **Платный Apple Developer ($99/год) + SideStore/AltStore или свой source** (полноценно, всегда)

Единственный путь к настоящему `NEPacketTunnelProvider` на актуальных iOS. С платным аккаунтом entitlement выдаётся self-serve, галочкой в Xcode. Дальше IPA раздаётся:
- через **AltStore/SideStore source JSON** (то, что ты и планировал — только сам IPA должен быть подписан твоим сертификатом),
- либо через TestFlight (до 10 000 тестеров, но нужна ревью Apple).

### 1.4 Принятое решение (пересмотрено)

**Одна сборка.** Основной способ установки: IPA, подписанный собственным сертификатом (бесплатный Apple ID через AltStore/SideStore, перевыпуск раз в семь дней). Это полноценная установка — приложение работает нативно, со своей песочницей.

LiveContainer остаётся как способ **посмотреть** на приложение без установки: вид, экраны, поведение интерфейса. Соединения в нём не будет.

Расширения `NEPacketTunnelProvider` в плане **нет** — почему, ниже.

Что из этого следует:

- отдельной сборки `lite` не будет — одна кодовая база, одна цель;
- требование LiveContainer (iOS 15+) перестало определять нижнюю границу, поэтому она поднята до **16.0**: `NavigationStack` вместо устаревшего `NavigationView`, `LabeledContent` вместо самодельной строки. Цена — iPhone 6s, 7 и SE первого поколения;
- локальный прокси **никуда не девается**: он и есть двигатель. Трафик доходит до него двумя путями — через профиль `.mobileconfig` (весь Wi-Fi) и через встроенный браузер (везде, включая сотовую).

```
clients/ios/
  AtlasCore/     обёртка над atlas-ffi (общая)
  AtlasApp/      приложение: экран, импорт ключа, состояние
  AtlasTests/    проверка в симуляторе
  AtlasBrowser/  встроенный браузер      ← следующий шаг
  AtlasTunnel/   NEPacketTunnelProvider  ← только если найдётся TrollStore
```

#### Расширения не будет: entitlement недоступен

`NEPacketTunnelProvider` требует `com.apple.developer.networking.networkextension`. Этот entitlement выдаётся **только платному аккаунту Apple Developer** ($99 в год) либо приходит с корпоративным сертификатом. Профиль подготовки на бесплатном Apple ID его не содержит — расширение не запустится, сколько его ни подписывай.

Платного аккаунта нет. Значит расширения не будет, и планировать его как основу нельзя.

**Но это отменяет не всё, а одну возможность из нескольких.** Установка IPA, подписанного бесплатным Apple ID (через AltStore/SideStore, с перевыпуском раз в семь дней), — это полноценная установка: приложение работает нативно, без LiveContainer, со своей песочницей и своими сокетами.

Что при этом остаётся и чего нет:

| | Работает без entitlement |
|---|---|
| Приложение установлено нативно, не в LiveContainer | ✅ |
| Локальный прокси слушает петлю | ✅ проверено в симуляторе |
| Встроенный браузер — **включая сотовую связь** | ✅ |
| Весь системный трафик Wi-Fi через профиль `.mobileconfig` | ✅ права не нужны |
| Весь системный трафик **сотовой** сети | ❌ только через расширение |

То есть недоступна ровно одна вещь: перехват системного трафика на мобильном интернете. Всё остальное — включая полное покрытие Wi-Fi — уже написано и проверено.

#### Что это меняет в порядке работ

Встроенный браузер поднимается в приоритете. Он не требует ни прав, ни профиля, ни Wi-Fi: это единственный способ пользоваться туннелем на сотовой связи, и без расширения — единственный вообще.

#### Единственный бесплатный путь к расширению — TrollStore

TrollStore подписывает IPA с произвольными entitlements, включая `networkextension`, бессрочно и бесплатно. Работает на **iOS 14.0–16.6.1 и 17.0**; на iOS 17.1+ — нет.

Значит вопрос конкретный: какая версия iOS на устройстве. Если она попадает в диапазон, расширение становится доступно даром, и `AtlasTunnel` возвращается в план. Если нет — путь через профиль и браузер остаётся единственным, и он рабочий.

#### Deployment target: iOS 16.0

Порог менялся дважды, и обе правки стоит оставить записанными.

Сначала стояло 14.0 с обоснованием «минимум, поддерживаемый LiveContainer». Обоснование неверное: README LiveContainer требует **`iOS/iPadOS 15+`**. Поддержка iOS 14 не давала ничего.

Затем 15.0 — ровно требование LiveContainer. Это было верно, пока LiveContainer считался способом установки. После пересмотра выше он остался способом **посмотреть** на приложение, и его требование перестало быть определяющим.

Итог — 16.0. Даёт `NavigationStack` вместо устаревшего `NavigationView` и `LabeledContent` вместо самодельной строки. Стоит — iPhone 6s, 6s Plus, SE 1-го поколения, 7 и 7 Plus, аппараты 2015–2016 годов.

**Для самого VPN разницы между версиями нет вовсе.** Сокеты BSD — всегда, `Network.framework` — с iOS 12, `NEPacketTunnelProvider` с `proxySettings` — с iOS 9, PAC — с iOS 3. Разрешение «Локальная сеть» из iOS 14 петли не касается, и это подтверждено проверкой в симуляторе. Порог — вопрос охвата устройств и удобства SwiftUI, не возможностей.

Верхняя граница не фиксируется: сборка идёт последним SDK и работает на актуальных iOS.

#### Про Liquid Glass и старые версии

Оформление iOS 26 нижней границе не мешает, и это следует из устройства, а не из везения: внешний вид **стандартных** элементов (`Form`, `Section`, `NavigationStack`, `Button`, `TextField`, `LabeledContent`) рисуют системные библиотеки на устройстве, а не приложение. Один и тот же файл на iOS 26 выглядит по-новому, на iOS 16 — по-старому. Ветвлений в коде для этого не нужно.

Три оговорки:

1. **Автоматическое обновление вида включается сборкой с SDK iOS 26.** Сейчас CI собирает агентом `macos-15`, то есть SDK 18 (в журнале проверки виден симулятор `OS:18.5`). Пока Liquid Glass не появится вовсе. Нужен агент с Xcode 26 — и порог iOS тут ни при чём, оформление привязано к SDK, а не к нижней границе.
2. **Явные вызовы Liquid Glass — только iOS 26.** `.glassEffect()`, `GlassEffectContainer` и подобное требуют `@available`. Вот здесь неосторожность и ломает старые версии — ровно как это уже случилось с `LabeledContent`.
3. **Порог 16 снял оговорку про `NavigationView`.** Устаревшего вызова больше нет, и под новым оформлением `NavigationStack` ведёт себя так, как задумано.

Решение: **оформление не задаём вручную**. Приложение пользуется стандартными элементами, а как их рисовать — решает система. Это единственный способ выглядеть уместно и на iOS 16, и на iOS 26 одной сборкой.

### 1.5 Как забирается трафик — три уровня, по возрастанию охвата

Ключевой момент: «локальный прокси» — это не урезанный режим. Он даёт системный охват, просто другим механизмом.

**Уровень 1 — свой сетевой стек внутри приложения.** Встроенный браузер и всё, что делает приложение, идёт через ядро всегда, без каких-либо настроек. Работает и на Wi-Fi, и на сотовой, и под LiveContainer.

**Уровень 2 — `.mobileconfig` с Wi-Fi payload.** Приложение генерирует профиль конфигурации и предлагает установить его в один тап. В профиле — прокси `127.0.0.1` и PAC-скрипт с правилами маршрутизации (что напрямую, что через туннель, что блокировать). После установки **весь системный трафик Wi-Fi** идёт через наше ядро: Safari, почта, мессенджеры, любое приложение на `URLSession`. Ни платного аккаунта, ни entitlements, ни supervised-режима.

**Уровень 3 — сотовая сеть.** Здесь честно: поле прокси в настройках сотовой сети iOS не показывает. Есть payload `com.apple.cellular` с полями `ProxyServer`/`ProxyPort` в конфигурации APN, но Apple ограничила его установку — требует supervised-устройство либо подпись оператора. **Это открытый исследовательский пункт** (см. `docs/08-ios-research.md`), а не обещание. До его закрытия сотовый трафик покрывает только уровень 1 и режим full.

### 1.6 Устройство пользователя как узел сети

Отдельно — про идею «сам телефон становится нодой». Она правильная и заложена в ярус T4, но на iOS у неё своя специфика:

| Роль | iOS lite | iOS full | Android | Desktop |
|---|---|---|---|---|
| **Клиент** (потребляет) | ✅ | ✅ | ✅ | ✅ |
| **Первый хоп** для другого клиента (WebRTC) | только на переднем плане | в фоне, пока активен туннель | ✅ фоновый сервис | ✅ всегда |
| **Точка выхода** (exit) | ❌ | ❌ | ⚠️ не рекомендуется | ✅ |
| **Раздача каталога** (gossip) | ✅ | ✅ | ✅ | ✅ |

Причина: iOS жёстко ограничивает фоновое выполнение. Приложение без активного Network Extension в фоне живёт секунды. Поэтому iPhone — **полноценный потребитель и раздатчик каталога**, но узлом-транспортом работает только пока экран активен.

Реальные узлы сети — Android (foreground service живёт неограниченно), десктопы и роутеры OpenWrt. Это не недостаток дизайна: телефон в кармане с мобильным трафиком и так плохой кандидат в релеи, а вот ноутбук друга за границей — отличный.

### 1.7 Технические ограничения iOS, которые надо держать в голове
- **Лимит памяти Network Extension — 50 МБ** (15 МБ на старых устройствах). Превышение = мгновенный kill. Это главный аргумент за Rust-ядро.
- Расширение может быть выгружено системой в любой момент → нужен быстрый (< 300 мс) холодный старт и восстановление состояния.
- Фоновая работа основного приложения жёстко ограничена → всё, что должно работать всегда, живёт в расширении.
- `NEDNSSettings`, `includedRoutes`/`excludedRoutes` — основной инструмент split-tunneling; per-app routing на iOS доступен только через MDM.

## 2. Android

Самая свободная платформа. `VpnService` даёт TUN-интерфейс без каких-либо особых разрешений и без root.

```
clients/android/
  app/            Kotlin + Jetpack Compose
  core/           JNI-мост к atlas-ffi (Rust, cargo-ndk)
  service/        AtlasVpnService : VpnService
```

Возможности, которых нет на iOS:
- **Per-app routing из коробки**: `addAllowedApplication()` / `addDisallowedApplication()` по имени пакета. Это прямо закрывает твою задачу «блокировки на отдельные приложения».
- **Режим без VpnService**: локальный SOCKS5 + DPI-десинхронизация (как ByeDPI) — трафик не покидает устройство, максимум скрытности.
- **Always-on VPN** + block-connections-without-VPN = встроенный kill switch.
- **QUIC/UDP** полностью доступен.

Сборка: `.apk` (universal + per-ABI splits) в GitHub Actions, подпись keystore из секретов репозитория.

## 3. Windows

```
clients/windows/
  atlas-tray/     Tauri (Rust + web UI)
  atlas-svc/      Windows Service (ядро, работает от SYSTEM)
  drivers/        WinTun (туннель) + WinDivert (desync-режим)
```

Два режима:
1. **Desync** — через WinDivert, как GoodbyeDPI: перехват и модификация исходящих пакетов, **без туннеля**. Мгновенно, ничего не замедляет.
2. **Full tunnel** — WinTun-адаптер + маршруты + kill switch через WFP (Windows Filtering Platform).

Артефакты: portable `.exe` (без установки, важно) + MSI. Подпись — по возможности; без сертификата будет SmartScreen-предупреждение, это надо честно писать в README.

## 4. macOS

```
clients/macos/
  AtlasMac/            SwiftUI menu-bar app
  AtlasSysExtension/   NETransparentProxyProvider / NEPacketTunnelProvider
```

Особенности:
- System Extension требует нотаризации Apple для распространения вне App Store; без неё — только с отключённым SIP или через ручное разрешение в Настройках.
- Альтернатива без entitlements: `utun`-интерфейс + `pfctl` из helper-процесса с правами (как делает большинство OSS-клиентов).
- Universal binary (arm64 + x86_64), артефакт `.dmg`.

**Про отсутствие MacBook:** это решаемо. GitHub Actions даёт бесплатные macOS-раннеры (`macos-14`, arm64) для публичных репозиториев. Там можно не только собирать, но и **запускать** — юнит-тесты, интеграционные тесты ядра, скриншот-тесты UI через XCUITest в headless-режиме. Полноценно проверить System Extension в CI не выйдет (нужны права и перезагрузка), но собрать, протестировать ядро и убедиться, что приложение стартует — вполне. Это же относится и к iOS: симулятор в CI прогоняет UI-тесты.

## 5. Linux

```
clients/linux/
  atlas-cli/      основной бинарь, headless
  atlas-gui/      Tauri
  packaging/      .deb, .rpm, AppImage, systemd unit
```

- Отдельная сборка под **OpenWrt** (ipk, mips/arm) — один роутер закрывает всю квартиру. Это очень сильный сценарий: настроил один раз, работают все устройства, включая телевизор и приставку.

## 6. Общий UI/UX — принципы

1. **Одна кнопка.** Главный экран — большая кнопка и статус. Всё остальное — за «Дополнительно».
2. **Никогда не показывать пользователю слово «VLESS»** на первом экране. Он не должен знать про протоколы. Приложение выбирает само.
3. **Честный статус**: не «Подключено», а «Подключено · 42 Мбит/с · через свою точку (Cloudflare)». Пользователь должен понимать, что происходит.
4. **Режим помощи** — отдельный экран с полным объяснением рисков, выключен по умолчанию.
5. **Импорт чужих ключей** — обязателен. Пользователь придёт со своими `vless://`, и это должно просто работать (вставка, QR, файл подписки).
6. **Экспорт своей точки** в виде ключа/QR — чтобы поделиться с родственниками.
7. **Полная локализация** ru/en с первого дня.

## 6a. Граница между ядром и клиентом

Ядро на Rust, клиенты — на Swift и Kotlin. Связывает их `atlas-ffi`:
восемь функций C ABI, заголовок лежит в репозитории
(`core/atlas-ffi/include/atlas.h`), собирается `cbindgen`.

```c
AtlasProxy *proxy = atlas_proxy_start(key, "127.0.0.1:0", NULL);
char *where = atlas_proxy_address(proxy);   /* «127.0.0.1:53017» */
/* … сюда же и ведёт PAC из .mobileconfig … */
char *stats = atlas_proxy_stats(proxy);     /* JSON для экрана состояния */
atlas_proxy_stop(proxy);
```

Порт `0` в адресе означает «любой свободный», и занятый узнаётся
обратно. Для сборки `lite` это существенно: фиксированный порт может
оказаться занят, а объяснить пользователю такую ошибку нечем.

Устройство границы намеренно скупое:

- никакой своей логики — всё, что она делает, делает `atlas-dial`,
  иначе поведение клиента разойдётся с поведением `atlas-proxy`;
- описание ключа (`atlas_key_describe`) отдаёт узел, порт, SNI, ALPN и
  метку — **но не учётные данные**: описание уходит в интерфейс и в
  журналы, а UUID даёт доступ к точке выхода;
- причина отказа забирается отдельным вызовом и **живёт в том же
  потоке**, где случился отказ, как `errno`. Обёртки обязаны читать её
  сразу и там же;
- остановка не рвёт уже открытые соединения: обрывать чужую загрузку
  на полуслове потому, что нажали «выключить», — худшее из поведений.

Проверяется граница не из Rust, а **настоящей программой на C**: так
сигнатуры читает сторонний компилятор из сгенерированного заголовка —
ровно как их прочитает Swift. Один из тестов гоняет через границу
настоящий трафик: поднимает точку выхода, программа на C идёт сквозь
прокси методом `CONNECT` и получает ответ назначения.

Чего у границы нет и о чём клиенту надо знать: паника в ядре роняет
приложение целиком (релиз собирается с `panic = "abort"`), а прокси
понимает только `CONNECT` — значит HTTP/3 и QUIC через него не пойдут.
Оба пункта — в реестре слабых мест.

### Профиль и правила — тоже из ядра

Клиенту не нужно уметь ни plist, ни JavaScript:

```c
/* Правила задаются при запуске, списками, а не строкой. */
AtlasProxy *proxy = atlas_proxy_start(key, "127.0.0.1:0", NULL,
                                      "{\"direct\":[\"gosuslugi.ru\"]}");
char *where = atlas_proxy_address(proxy);       /* «127.0.0.1:53017» */
char *profile = atlas_mobileconfig("Дом", where, 1, NULL);
char *rules = atlas_proxy_pac(proxy);           /* показать пользователю */
```

Скрипт правил прокси отдаёт **сам**, по `http://127.0.0.1:порт/proxy.pac`,
и профиль указывает именно туда. Отсюда важное следствие: правила
меняются без переустановки профиля — пользователь правит список
исключений в приложении, и следующий же запрос системы получает новый
скрипт.

`atlas_proxy_pac` существует ради того, чтобы правила можно было
**показать**. Правила маршрутизации, которых не видно, — это правила,
которым нельзя доверять: каждое исключение означает, что оператор связи
увидит поход пользователя на этот сайт.

Проверяется всё тем, кто это будет читать: PAC — исполнением в
настоящем движке JavaScript (включая проверку, что домен-двойник
`notgosuslugi.ru` не проскочит мимо туннеля по правилу `gosuslugi.ru`),
профиль — разбором сторонним разборщиком plist. Чего проверить нельзя —
поведение настоящего iPhone; это записано в реестре слабых мест.
