# 04 — Control plane: криптография, распределение точек, «блокчейн»

> Здесь живёт математика проекта. Это самая недооценённая часть любого VPN — и именно на ней ломаются все бесплатные сервисы.

---

## 1. Задача, которую почти никто не решает

Допустим, у нас есть 50 000 точек выхода. Как **доставить** пользователю рабочую точку так, чтобы противник, который тоже скачал наше приложение, **не смог получить их все и забанить**?

Это называется **проблема раздачи мостов** (bridge distribution problem), и она сложнее, чем сам протокол обхода.

Как это ломается на практике:
- **Телеграм-канал с ключами** → противник подписан → баним всё за час. Так умирают 99 % бесплатных «VPN-ботов».
- **Публичный API** → противник качает API → баним всё.
- **Ключ в приложении** → противник ставит приложение → баним.

**Вывод: точки нельзя раздавать. Точки надо выдавать — избирательно, анонимно и с памятью о поведении.**

## 2. Криптографический фундамент

### 2.1 Примитивы

| Назначение | Классика | Постквантовое | Режим |
|---|---|---|---|
| Подпись дескрипторов | Ed25519 | ML-DSA-65 (Dilithium3) | **обе, обязательно обе** |
| Обмен ключами | X25519 | ML-KEM-768 (Kyber) | гибрид X25519MLKEM768 |
| Шифрование | ChaCha20-Poly1305 / AES-256-GCM | — | AEAD |
| Хэш / KDF | BLAKE3 | BLAKE3 | — |
| Анонимные креденшелы | BBS+ / CMZ над Ristretto255 | — | zero-knowledge |
| Пароль → ключ | Argon2id | — | для локального хранилища |

Гибридная подпись — не паранойя, а страховка: ML-DSA молод, Ed25519 квантово уязвим. Валиден дескриптор только если **обе** подписи верны.

### 2.2 Иерархия ключей

```
Root Authority (offline, разделён по Shamir 3-из-5, у независимых людей)
    │  подписывает раз в квартал
    ▼
Directory Signing Keys (N=5, ротация 90 дней)
    │  подписывают головы Merkle-лога
    ▼
Relay Descriptors (подписаны своим ключом релея, включены в лог)
    │
    ▼
Session credentials (эфемерные, TTL 6–24 ч)
```

Корневой ключ **никогда** не в сети. Разделён по схеме Шамира (3 из 5) между людьми в разных юрисдикциях. Компрометация одного участника ничего не даёт.

## 3. Каталог как прозрачный лог (Merkle / Certificate Transparency)

### 3.1 Структура
Каталог — **append-only Merkle-дерево** дескрипторов. Каждая «голова» (root hash + timestamp + counter) подписана Directory Signing Keys.

Что это даёт:
- **Клиент проверяет включение** дескриптора по компактному Merkle-пруфу (log n хэшей, ~320 байт для 10⁶ записей) — не скачивая весь каталог.
- **Невозможен split-view**: если противник (или скомпрометированный сервер) покажет одному пользователю один каталог, а другому — другой, это обнаружится при сверке голов между клиентами (gossip). Ровно механика Certificate Transparency.
- **Аудируемость**: любой может проверить, что каталог не переписывали задним числом.

### 3.2 Про «блокчейн» — честно

Ты предложил свой блокчейн. Разберу прямо, где он нужен, а где будет вредом.

**Где блокчейн НЕ нужен и вреден:**
- Как хранилище каталога. Блокчейн — это медленно (секунды–минуты на финализацию), дорого по трафику (нужна вся цепочка или лёгкий клиент), и главное — **публично**. Публиковать список точек выхода в неизменяемый публичный реестр = подарить противнику вечный, самообновляемый список целей. Это прямая противоположность нашей цели G4.
- Как консенсус. Нам не нужен глобальный консенсус по порядку событий. Нам нужна **аутентичность** и **отсутствие split-view** — это решается подписями + Merkle-логом + gossip'ом, на три порядка дешевле.

**Где криптоэкономика реально имеет смысл (Фаза 4):**
1. **Якорение голов лога.** Раз в сутки публиковать root hash в существующую публичную цепь (или в OpenTimestamps/Bitcoin через агрегатор). Стоит копейки или ноль, даёт неопровержимую временную метку и делает невозможным незаметное переписывание истории. Это **не свой блокчейн**, это использование чужого как нотариуса — и это правильный инженерный ответ.
2. **Стимулирование волонтёров.** Вот здесь токен осмыслен: волонтёр отдаёт полосу → получает подтверждаемый другими узлами кредит → тратит его на приоритетный доступ. Но это нужно **только если** карма-репутации окажется недостаточно. Начинать с токена — значит привлечь спекулянтов, KYC-риски и внимание регуляторов раньше, чем появятся пользователи.

**Решение проекта:**
> Фаза 1–3 — подписанный Merkle-лог + gossip, без цепи. Фаза 4 — якорение голов в публичной цепи и, опционально, кредитная система для волонтёров. Своя цепь с нуля — нет: это месяцы работы ради свойств, которые нам не нужны.

Если после реализации Фазы 3 захочется полноценной цепи — вернёмся с реальными данными о том, какую проблему она решает. Проектировать её «потому что круто» — самый быстрый способ утопить проект.

## 4. Распределение точек: Lox-подобная схема

Ключевая часть. Основано на исследованиях **Salmon** (2016) и **Lox** (PETS 2023, Cannon & Goldberg) по раздаче Tor-мостов.

### 4.1 Идея
Пользователь получает **анонимный креденшел** — криптографический объект, который:
- доказывает «я легитимный пользователь уровня доверия K»,
- **не раскрывает, кто именно** этот пользователь (zero-knowledge, слепые подписи),
- **не позволяет** связать два его обращения между собой (unlinkability),
- при этом **накапливает историю**: если выданные ему точки блокируются, его уровень падает.

### 4.2 Уровни доверия

| Уровень | Как получить | Точек за раз | Может приглашать |
|---|---|---|---|
| 0 (untrusted) | открытая регистрация с proof-of-work / капчей | 1, из «расходного» пула | нет |
| 1 | 1 неделя без блокировки выданных точек | 2 | нет |
| 2 | 2 недели | 3 | 1 инвайт / 2 нед |
| 3 | 1 месяц + вклад (волонтёрство) | 4 | 2 инвайта / нед |
| 4 (trusted) | 3 месяца, инвайт от уровня 3+ | 6, из «премиального» пула | 4 инвайта / нед |

### 4.3 Почему это работает против противника

Противник хочет перечислить точки. Он может:
- **Массово регистрироваться на уровне 0** → получит по 1 точке из расходного пула. Каждая заблокированная им точка → он теряет уровень и не растёт. Расходный пул специально состоит из дешёвых, легко пересоздаваемых T1-точек. Ценные T3/T5-точки он не увидит **никогда**.
- **Внедриться и вырасти до уровня 4** → должен несколько месяцев *не блокировать* выданные точки. То есть, чтобы получить доступ к ценному пулу, противник обязан несколько месяцев позволять людям обходить блокировки. Экономически он проигрывает.
- **Атаковать через инвайты** → инвайт-дерево отслеживается: если поддерево массово «сжигает» точки, штрафуется вся ветка вместе с пригласившим. Приглашать своих незнакомцев становится дорого.

Это превращает перечисление из технической задачи в **экономическую игру, где противник платит временем, а мы — дешёвыми точками**.

### 4.4 Формально

Креденшел — набор атрибутов $(\text{id}, \text{level}, \text{invites}, \text{since}, \text{blockages}, \text{bucket})$ под алгебраическим MAC (схема CMZ/BBS+ над Ristretto255).

Обновление уровня — протокол «show-and-reissue»:
1. клиент доказывает в ZK владение валидным креденшелом и что $\text{now} - \text{since} \geq \tau_{\text{level}}$;
2. предъявляет одноразовый nullifier (защита от двойной траты) — hash от скрытого id, раскрывающий только «этот креденшел уже использован в этой эпохе»;
3. получает новый креденшел с level+1, **невзаимосвязываемый** со старым.

Выдающая сторона видит только: «кто-то валидный, уровня 2, перешёл на 3». Кто именно — неизвестно.

## 5. Транспорт каталога: gossip по N независимым каналам

Каталог бесполезен, если до него нельзя добраться. Поэтому головы лога и фрагменты дескрипторов распространяются **одновременно** по каналам с разными профилями блокировки:

| Канал | Как | Блокируется |
|---|---|---|
| **DoH TXT-записи** | голова лога в TXT известного домена, забираем через Google/Cloudflare DoH | сложно (сломает DNS) |
| **Cloudflare KV / Workers** | подписанный blob по URL | средне |
| **GitHub raw / Pages** | подписанный blob в публичном репо | легко (GitHub уже частично режут) |
| **IPFS / Iroh** | по CID, через публичные шлюзы | средне |
| **Nostr-релеи** | подписанное событие в N релеев | сложно (много релеев) |
| **BitTorrent DHT** | ключ = hash эпохи, значение = голова | сложно (DHT распределён) |
| **Telegram-канал** | подписанный blob (не ключи! только голова лога) | легко |
| **P2P между клиентами** | клиент, у которого есть свежая голова, отдаёт соседям по WebRTC | **невозможно** |

Клиент опрашивает каналы **параллельно**, берёт первый успешный, затем **сверяет** головы между каналами. Расхождение = сигнал атаки split-view → предупреждение и переход в консервативный режим.

**Ключевой момент:** по этим каналам ходят **головы лога и Merkle-пруфы**, а не сами ключи доступа. Даже полный перехват канала не даёт противнику рабочих точек — только возможность узнать, что каталог существует.

## 6. Репутация релеев

Каждый релей имеет оценку, вычисляемую из анонимных отчётов клиентов:

$$R = w_1 \cdot \text{uptime} + w_2 \cdot \log(\text{throughput}) + w_3 \cdot (1 - \text{block\_rate}) - w_4 \cdot \text{anomaly}$$

- Отчёты клиентов агрегируются **с дифференциальной приватностью** (добавление шума Лапласа) — чтобы отчёт нельзя было использовать для деанонимизации отправителя.
- `anomaly` растёт, если релей ведёт себя как ловушка: аномально высокая доступность при аномально низкой нагрузке, попытки MITM (детектится по несовпадению pinned-ключей), нестабильные RTT-паттерны.
- Релеи с низким $R$ автоматически выпадают из выдачи.

**Защита от Sybil:** новый релей входит в пул с нулевым весом и растёт медленно; для попадания в премиальный пул нужен поручитель уровня 4.

## 7. Приватность самого клиента

- **Никакой регистрации**, e-mail, телефона. Идентичность = локально сгенерированный ключ.
- Все запросы к control plane идут **через уже поднятый туннель** или через WebRTC — control plane не видит реальный IP пользователя.
- Локальное хранилище шифруется ключом из Keychain/Keystore (Argon2id, если есть пароль).
- **Телеметрия — только opt-in, только агрегированная, только с DP-шумом.** Никаких «анонимных идентификаторов установки».
- Режим **paranoid**: отключает всю телеметрию, всё P2P, оставляет только T3/T5 (своя точка) и multi-hop.

---

## 8. Отзыв и аварийное реагирование

- **Короткий TTL** (6–24 ч) — основной механизм. Скомпрометированный дескриптор протухает сам.
- **Revocation list** в каждой голове лога (компактный, через Bloom/Cuckoo-фильтр).
- **Kill switch каталога**: если корневой ключ скомпрометирован, подписывается специальное событие, клиенты переходят на резервный набор ключей (зашит в бинарь, отдельная ветка иерархии).
- **Canary**: регулярно публикуемое подписанное заявление «нас не принуждали». Пропажа canary — сигнал.

## 9. Что реализуем и в каком порядке

| Приоритет | Компонент | Фаза |
|---|---|---|
| P0 | Дескрипторы + гибридные подписи + верификация | 1 |
| P0 | Merkle-лог + пруфы включения | 1 |
| P0 | Gossip по 3 каналам (DoH TXT, CF KV, GitHub) | 1 |
| P1 | Репутация релеев + DP-агрегация отчётов | 2 |
| P1 | Инвайт-дерево + уровни доверия (упрощённо, без ZK) | 2 |
| P2 | Полноценные анонимные креденшелы (Lox-подобные, ZK) | 3 |
| P2 | Gossip по остальным каналам + P2P-распространение | 3 |
| P3 | Якорение голов в публичной цепи | 4 |
| P3 | Кредитная система для волонтёров | 4 |
