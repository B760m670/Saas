# Бот Gloria VPN

Запускается на машине, где стоит панель. Там уже есть Docker, PostgreSQL и
Caddy, и туда же бот ходит за ключами — все обращения остаются внутри
машины.

## Из чего собран

| Крейт | За что отвечает | Чем проверен |
|---|---|---|
| `atlas-bot` | экраны, кнопки, тексты, витрина | обычными тестами |
| `atlas-panel` | выдача и продление в Remnawave | обычными тестами |
| `atlas-store` | заказы, платежи, подписки | живым PostgreSQL |
| `atlas-tg` | разбор обновлений и отправка | обычными тестами |
| `gloria` | соединение проводов | только запуском |

Ни один крейт, кроме `gloria`, не ходит в сеть: они собирают запросы и
разбирают ответы. Поэтому ошибка в разборе ловится тестом, а не подбором
на живом сервисе.

## Что нужно задать

Переменные окружения. Секреты сюда, в репозиторий, **не попадают**.

| Переменная | Обязательна | Что это |
|---|---|---|
| `GLORIA_BOT_TOKEN` | да | токен от @BotFather |
| `GLORIA_PANEL_URL` | да | адрес API панели, см. ниже |
| `GLORIA_PANEL_TOKEN` | да | Remnawave → API-токены |
| `GLORIA_DATABASE_URL` | да | `postgres://gloria:ПАРОЛЬ@127.0.0.1:6767/gloria` |
| `GLORIA_SQUADS` | да | UUID отрядов через запятую |
| `GLORIA_ADMINS` | нет | ваш номер в Telegram |
| `GLORIA_PAY_LINK` | нет | ссылка на перевод — та, что за QR-кодом в банке |
| `GLORIA_API_ADDR` | нет | где слушать мини-приложение, по умолчанию `127.0.0.1:8081` |
| `GLORIA_BOT_USERNAME` | нет | имя бота без `@` — из него строится реферальная ссылка |
| `GLORIA_YOOKASSA_SHOP_ID` | нет | номер магазина в ЮKassa |
| `GLORIA_YOOKASSA_SECRET` | нет | секретный ключ магазина |
| `GLORIA_WATA_TOKEN` | нет | токен терминала WATA |
| `GLORIA_MINIAPP_URL` | нет | адрес кабинета — из него кнопка «Меню» |

Бот отказывается стартовать, если чего-то обязательного нет, и **называет
переменную по имени**. «Что-то не настроено» в четыре часа ночи — это час
поисков.

Без `GLORIA_PAY_LINK` бот работает, но на счёт отвечает «приём оплаты ещё
настраивается, напишите в поддержку». Без `GLORIA_ADMINS` подтверждать
оплаты будет некому.

Где взять UUID отряда: панель → Internal Squads → нужный отряд, его
идентификатор в адресе страницы.

### Адрес панели — петлевой, а не публичный

`GLORIA_PANEL_URL` — это `http://127.0.0.1:3000`, а **не** тот адрес, по
которому вы открываете панель в браузере.

Панель за Caddy закрывает `/api/*` от внешнего мира: по публичному адресу
запрос упирается в `404` при живом и совершенно правильном токене. Это
намеренно — так панель не подтверждает наличие API тому, кто его щупает.

Бот стоит на той же машине, и панель публикует API на петлю. Обращение
туда не выходит наружу вовсе и не зависит от чужих настроек Caddy.

`http` здесь допустим ровно поэтому: требование `https` существует ради
того, чтобы токен панели не шёл по сети открытым, а по `127.0.0.1` он по
сети и не идёт. Для любого другого имени бот по-прежнему требует `https`,
и проверка смотрит на начало адреса — `http://127.0.0.1.чужое.example`
петлевым не считается.

Порт уточните по `docker ps`; у публикующего API контейнера это обычно
`127.0.0.1:3000`.

### Порт базы

Порт базы в `GLORIA_DATABASE_URL` — **не 5432**. Панель публикует свой
PostgreSQL на другой порт хоста; какой именно, показывает
`docker ps --format '{{.Names}}   {{.Ports}}'` слева от стрелки (обычно
`127.0.0.1:6767`). Подробнее — в `db/README.md`.

## Как запустить

```bash
# 1. Компилятор C. Rust линкует через cc, и у части зависимостей (libc,
#    ring, typenum) есть скрипты сборки. На свежей Ubuntu их нет, и сборка
#    падает на «error: linker `cc` not found».
apt-get update && apt-get install -y build-essential pkg-config

# 2. База — если ещё не создана, см. db/README.md
# 3. Сборка
cd bot && cargo build --release

# 4. Настройки
cat > /etc/gloria.env <<'ENV'
GLORIA_BOT_TOKEN=…
GLORIA_PANEL_URL=https://panel.…
GLORIA_PANEL_TOKEN=…
GLORIA_DATABASE_URL=postgres://gloria:…@127.0.0.1:6767/gloria
GLORIA_SQUADS=…
GLORIA_ADMINS=…
ENV
chmod 600 /etc/gloria.env

# 5. Проверка вручную
set -a; . /etc/gloria.env; set +a
./target/release/gloria
```

При успехе печатается строка вида
`Бот запущен. Config { bot_token: "<скрыт>", … }` — секреты в неё не
попадают намеренно: вывод уходит в журнал, а журнал читают и пересылают.

## Службой

Пока бот запущен из ssh, он умирает вместе с сессией — вместе с ним
пропадают и кабинет, и приём оплаты. Служба переживает и обрыв связи, и
перезагрузку машины, и собственный сбой.

Один раз:

```bash
# Отдельный пользователь без входа и без домашнего каталога. Бот разбирает
# то, что пришло из сети; ошибка в разборе под root — это вся машина.
useradd --system --no-create-home --shell /usr/sbin/nologin gloria

# Собранное лежит отдельно от исходников: иначе пересборка попыталась бы
# переписать файл работающего процесса и упёрлась бы в «Text file busy».
install -d -o root -g root /opt/gloria
install -m 755 bot/target/release/gloria /opt/gloria/gloria

# Настройки читает служба, а не вы: чужим читать их незачем.
chown root:gloria /etc/gloria.env && chmod 640 /etc/gloria.env

install -m 644 deploy/systemd/gloria-bot.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now gloria-bot
```

Проверка:

```bash
systemctl status gloria-bot
journalctl -u gloria-bot -f
```

В журнале должны быть те же две строки, что и при запуске руками:
`Мини-приложение слушает 127.0.0.1:8081` и `Бот запущен. Config { … }`.

Права у службы урезаны: диск только для чтения, повышение прав запрещено,
из семейств адресов оставлены лишь нужные. Бот ничего не пишет на диск, и
это ограничение стоит ровно на случай ошибки в разборе того, что пришло
из сети.

## Обновление

```bash
cd /opt/gloria-src && ./deploy/gloria-update.sh
```

Сценарий делает всё по порядку: обновляет исходники, накатывает новые
миграции, собирает, выкладывает мини-приложение, подменяет двоичный файл
и перезапускает службу. Сборка идёт **до** остановки, поэтому простой —
секунды копирования, а не минуты компиляции.

Если бот не поднялся, сценарий покажет последние строки журнала и вернёт
ошибку, а не отрапортует об успехе.

## Что умеет сегодня

**Покупатель.** `/start` включает пробные три дня сразу, без кнопок и
запросов: каждый шаг между «зашёл» и «работает» теряет часть людей. Дальше
меню — подписка, продление, подключение, помощь. Выбор тарифа выставляет
счёт на **уникальную сумму**, по которой платёж потом узнаётся.

При вводе «/» Telegram показывает подсказку: `/start`, `/connect`,
`/help`. Список задаётся **из кода при каждом запуске**, а не однажды
руками в BotFather, — по той же причине, по которой правила ответов панели
лежат в репозитории: настройка, живущая только на чужом сервере,
восстанавливается по памяти и не восстанавливается.

Каждая команда обязана вести туда, что обещает подсказка. `/help` когда-то
показывал экран подписки — команда есть, помощи по ней нет; на это теперь
стоит тест, сравнивающий команду с одноимённой кнопкой.

### Всё происходит в кабинете, а не в переписке

Если задан `GLORIA_MINIAPP_URL`, бот перестаёт быть местом, где живёт
подписка, и становится входом в неё.

Слева от поля ввода появляется кнопка **«Открыть VPN»**. А все четыре
кнопки главного меню ведут **в кабинет, каждая в свой раздел**: «Продлить»
— сразу к тарифам, «Подключить» — сразу к настройке, «Помощь» — к
поддержке. Раздел передаётся в адресе после решётки (`…/#plans`), потому
что у кнопки мини-приложения нет ничего, кроме ссылки; разбирает его
`route()` в `site/index.html`.

Ссылка на подписку из переписки при этом **убрана**. Она нужна ровно до
тех пор, пока её негде показать иначе; в кабинете она лежит вместе с
кнопкой «скопировать» и переходом прямо в приложение. Два места для одного
и того же — это одно из них, которое отстаёт: мы это уже проходили, когда
кабинет писал «Истекла» при работающем VPN.

Без `GLORIA_MINIAPP_URL` остаются прежние кнопки с перепиской. Это не
запасной путь на всякий случай, а рабочее состояние: переменная
необязательна, и бот без неё обязан оставаться полезным. На оба состояния
стоят тесты.

Кнопка у поля ввода без адреса не ставится вовсе: ведущая в никуда хуже
отсутствующей.

**Владелец** (кто указан в `GLORIA_ADMINS`):

```
/pending           открытые счета: сумма, тариф, кому
/ok 198.99         подтвердить платёж по сумме
/revoke 123456789  перевыпустить ссылку человеку
```

Эти три видны в подсказке **только владельцу** — отдельной областью на его
чат. Показывать их всем не дыра (бот всё равно проверяет, кто пишет), но
это приглашение нажать на то, что откажет.

`/revoke` нужен, когда ссылка утекла: адрес подписки сам по себе пропуск,
и отозвать его иначе нечем. Старая умирает сразу, человек получает новую
сообщением. Ту же кнопку он может нажать и сам — в кабинете.

О каждом новом счёте владелец узнаёт сразу, не заглядывая в `/pending`.
Счёт живёт двадцать минут, и человек, который заплатил и ждёт, за это
время успевает решить, что его обманули.

После `/ok` покупатель получает сообщение сам: «оплата получена, подписка
до такого-то». Тишина после платежа читается как «деньги пропали», и
следующим сообщением было бы обращение в поддержку.

Повторное `/ok` по тому же счёту ничего не меняет — проверено тестом:
нажать дважды, не заметив, легко.

## Сколько устройств

`catalog::DEVICES` — **3**. Число уходит в три места: в тариф на витрине,
в ответ мини-приложению и в `hwidDeviceLimit` при заведении пользователя в
панели. Четвёртое — запасное значение в `site/index.html`, оно
показывается, когда сервер не ответил, и обязано совпадать.

**Панель принимает это число только при создании.** Уже заведённым
пользователям бот предел не меняет никогда: очередь возит в панель одну
лишь дату. Поменяли константу — новые получат новое, старые останутся с
прежним, и поправить их можно только руками в панели.

**И панель может не послушаться.** У пользователя, заведённого ботом с
`hwidDeviceLimit: 4`, в панели оказалось `3` — то есть наше число она
приняла не буквально. Скорее всего, действует общая настройка HWID, и
предел пользователя ею ограничен. Проверять надо там, а не в коде: если
панель говорит одно, а витрина обещает другое, врёт витрина.

## Приём оплаты

Два способа, и бот выбирает сам: если ключи ЮKassa заданы — счёт открывает
она, иначе показываются реквизиты для перевода вручную.

### WATA

```
GLORIA_WATA_TOKEN=…
```

Токен терминала из личного кабинета. Терминал у WATA — точка приёма под
конкретный вид деятельности; ссылка создаётся для того терминала, чей токен
стоит в заголовке.

**Если заданы ключи и WATA, и ЮKassa, счёт открывает WATA.** Она отдаёт
СБП, карты, T-Pay и SberPay одной ссылкой, а у ЮKassa для нерезидентов СБП
нет вовсе. Правило записано в `Config::accepts_wata`, а не разбросано по
коду.

Адрес уведомлений: `https://<домен>/api/pay/wata`.

**Предоплатные уведомления в личном кабинете надо выключить.** У них ответа
ждут 10 секунд и, не дождавшись, отклоняют транзакцию, не обращаясь в банк.
Наш обработчик за это время не обязан успеть: он ходит в API за настоящим
состоянием. У постоплатного ждут минуту и повторяют 32 часа — этого хватает
с запасом.

Уведомления WATA **подписаны** (`X-Signature`, RSA SHA512 по нетронутому
телу), и подпись мы не проверяем. Не по недосмотру: повторный запрос
сильнее. Подпись доказывает, что тело пришло от WATA и не изменилось по
дороге; ответ на наш собственный запрос доказывает то же самое **и**
показывает состояние на текущий момент, а не на момент отправки. Опоздавшее
или повторное уведомление подпись не отличит, а ответ API отличит.

### ЮKassa

```
GLORIA_YOOKASSA_SHOP_ID=…
GLORIA_YOOKASSA_SECRET=…
```

Ключи проверяются **при запуске**: узнать о негодном ключе в тот момент,
когда человек уже нажал «Оплатить», — значит узнать об этом от него.

Способ оплаты выбирает покупатель на странице ЮKassa — доступно то, что
включено в магазине. СБП там самый выгодный нам (от 0,4 % против ~3,5 % по
карте), но навязывать его мы не стали: не умеющий платить выбранным
способом не заплатит вовсе, а потерянная продажа стоит дороже шести рублей
разницы.

Главное — покупатель платит через страницу ЮKassa и **видит название
магазина, а не чьё-либо имя**. При переводе вручную ссылка прячет номер
телефона, но имя получателя банк плательщика всё равно покажет; это и есть
причина, по которой ручной способ остаётся запасным.

Уведомления настраиваются в личном кабинете ЮKassa: события
`payment.succeeded` и `payment.canceled`, адрес —
`https://<домен>/api/pay/yookassa`.

**Уведомлению мы не верим.** Оно не подписано ничем, а адрес открыт наружу
— иначе ЮKassa до него не достучится. Из тела берутся только событие и
номер платежа; ни суммы, ни состояния оттуда не читают. Дальше бот сам
идёт в ЮKassa за настоящим состоянием: ответ приходит по TLS на запрос с
нашим ключом, и подделать его, не имея ключа, нельзя. Адрес отправителя —
второй рубеж, а не первый.

Повторную доставку ЮKassa делает, пока не получит успех. Второй раз не
даёт ни дня: зачисление опирается на номер платежа, и это проверено
тестом.

### Перевод вручную

Запасной способ: **перевод по ссылке** на карту владельца, подтверждение
вручную. Никакого оформления он не требует и работает, пока платёжный
сервис не подключён.

```
GLORIA_PAY_LINK=https://…
```

Ссылку выдаёт банковское приложение — это то же, что стоит за QR-кодом
перевода. Бот ставит её на кнопку «Оплатить» под счётом — тем же
словом, что и счёт от платёжного сервиса: покупатель в обоих случаях
делает одно, и разными названиями мы описывали бы ему разницу, которая
касается только нас.

**Плательщик увидит и номер, и имя получателя.** У Т-Банка постоянной
ссылки на перевод без номера нет: тот QR, который он даёт, — платёжный QR
СБП, и номер в нём не оформление, а содержимое. Имя показывает банк
плательщика, и этим экраном распоряжается он.

Скрыть то и другое умеет только приём через платёжный сервис, где виден
магазин. Владелец это взвесил и решил, что видимые реквизиты его
устраивают.

При запуске значение обязано начинаться с `https://`: строку без адреса
Telegram не примет на кнопку, и отказ вылез бы у покупателя на каждом
счёте вместо оплаты.

Если в адресе виден номер телефона — вида
`?requisiteNumber=+79001234567` — бот печатает предупреждение в журнал, но
работать не отказывается. Отказ здесь стоял раньше и мешал: ссылки без
номера у Т-Банка попросту нет.

**Сумму человек вводит сам** — ссылка с зашитой суммой здесь не годится:
по сумме и опознаётся платёж (см. ниже).

Платёж узнаётся по **уникальной сумме**: 199 ₽ выставляется как 198,99 ₽.
Копейки вычитаются, а не прибавляются, — так мы никогда не берём больше
обещанного. Круглая сумма не достаётся никому: заплативший «по памяти»
не закроет чужой счёт.

Счёт в ЮKassa открывают юридическому лицу, ИП и самозанятому; физическому
лицу `shopId` и секретный ключ не выдают. Это единственное препятствие к
автоматическому приёму — техническое всё готово.

## Мини-приложение

Бот поднимает маленький HTTP-сервер и отдаёт странице состояние подписки.
Слушает он **только петлю**; наружу его выставляет Caddy на том же домене,
где лежит сама страница:

```caddyfile
handle /api/* {
    reverse_proxy 127.0.0.1:8081
}
handle {
    root * /var/www/gloria
    file_server
}
```

Тот же домен выбран не для простоты: запрос идёт с того адреса, откуда
пришла страница, поэтому не нужен ни CORS, ни второй сертификат.

Кто спрашивает — определяется подписью Telegram в заголовке
`X-Init-Data`, а не номером в запросе. Номер, присланный клиентом, не
удостоверяет ничего: подставив чужой, любой получил бы чужую ссылку на
подписку.

Сегодня отвечает один путь:

```
GET  /api/me             срок, статус, ссылка на подписку, реферальная
POST /api/reissue        перевыпустить ссылку, вернуть новое состояние
POST /api/pay/yookassa   уведомление о платеже — от ЮKassa, не от страницы
POST /api/pay/wata       то же от WATA
```

Два последних — единственные пути без подписи Telegram: приходят они не из
мини-приложения. Чем они защищены — выше, в разделе про приём оплаты. Оба
сводятся к одному: из уведомления берётся только номер платежа, а состояние
спрашивается у сервиса запросом с нашим ключом.

`reissue` — только `POST`: он меняет состояние, и по ссылке из чата или
предзагрузкой браузера случаться сам собой не должен.

Проверить, не открывая Telegram, — должно быть `401`, потому что подписи
у `curl` нет:

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://<домен>/api/me
```

`401` — сервер на месте и никого не пускает без подписи. `502` — бот не
запущен. `404` — Caddy не проксирует `/api/*`.

## Как дата попадает в панель

Не прямым вызовом после оплаты, а очередью. В базе рядом с нашей датой
лежит `panel_expires_at` — та, которую панель подтвердила. Разошлись —
значит есть работа; бот разбирает её на каждом круге цикла, то есть не
реже раза в полминуты.

Прямой вызов после оплаты теряется при обрыве связи ровно в тот момент,
когда деньги уже взяты. Очередь при обрыве просто остаётся непустой.

Гасить просроченных не нужно: панель меняет статусы сама по своей дате —
у неё для этого есть собственные события `user.expired`, `user.disabled`.
Наша забота одна: чтобы её дата совпадала с нашей.

**Прошедшие даты в очередь не попадают.** Панель отказывается ставить срок
задним числом и отвечает `400`. Такая строка не уедет никогда, а очередь
долбилась бы в неё каждые полминуты — именно это у нас и происходило
сутками. Терять нечего: просроченного панель гасит сама по своей дате.

Отметка о согласовании ставится **той датой, которую отвозили**. Если
между чтением очереди и ответом панели человек оплатил ещё раз, отметка
не применится и строка останется в очереди — иначе продление пропало бы
молча.

## Как правка в панели попадает к нам

Очередь возит даты **в одну сторону**. Пока панель никто не трогает
руками, этого хватает. Стоит продлить кого-нибудь прямо в панели — и
раньше бот об этом не узнавал никак: кабинет показывал «Истекла»
человеку, у которого VPN работает. На это мы и напоролись.

Поэтому при каждом обращении человека — сообщение боту или открытие
кабинета — его запись сверяется с панелью:

| Что в базе | Что делаем |
|---|---|
| `expires_at` ≠ `panel_expires_at`, дата в будущем | ничего: работа уже в очереди, решает она |
| `expires_at` ≠ `panel_expires_at`, дата в прошлом | сверяемся: очередь такую не повезёт |
| совпадают, а панель говорит другое | принимаем дату панели |
| панель отвечает `404` | забываем связь, заведём заново |

Вторая строка — не мелочь, а выход из тупика. Очередь прошедшие даты не
берёт, и если бы сверка тоже за них не бралась, такой человек не
согласовался бы никогда: кабинет вечно показывал бы «Истекла» при
работающем VPN.

**Условия взаимоисключающие, и это главное.** Пока наше изменение не
увезено, панель не спрашиваем вовсе; спрашиваем только когда своих
изменений нет. Иначе очередь и сверка тянули бы одну дату в разные
стороны, и она качалась бы между двумя значениями бесконечно.

Приоритет тоже отсюда: **оплата важнее ручной правки.** Заплатил человек
— его дата уедет в панель и перекроет то, что там поставили руками.

Принятая дата пишется сразу в оба поля. Записать только `expires_at`
значило бы поставить строку в очередь и на следующем же круге отменить
принятую правку.

Расхождение меньше минуты правкой не считается: мы храним секунды, панель
— строку ISO с миллисекундами, и обратный перевод может отличаться на
доли секунды. Без допуска это выглядело бы как вечная правка.

Заодно сверяется **ссылка на подписку**. Пользователя могли пересоздать в
панели — тогда у него новый `shortUuid`, а бот раздавал бы прежний адрес,
которого больше нет. Ровно этим объяснялось «ссылка из панели работает, а
из бота — нет».

Цена — один запрос к панели на обращение человека. При нынешних числах
незаметно; когда станет заметно, сверку надо двигать в фоновый круг с
отметкой «когда проверяли в последний раз».
