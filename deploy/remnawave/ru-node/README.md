# RU-узел: каскад через Нидерланды

Зачем он и от чего помогает — `docs/18-ru-node.md`. Здесь — порядок.

| Файл | Что |
|---|---|
| `check.sh` | проверка машины: адрес в белом списке, 443, что отрезано, путь до NL |
| `make-profile.sh` | сборка профиля из подписки служебного пользователя, с ключами |
| `profile.json` | профиль конфигурации для панели: вход, выход в NL, маршрут |

## 0. Проверить машину

До установки, на свежем сервере:

```bash
curl -sSLO https://raw.githubusercontent.com/B760m670/Saas/claude/multiplatform-vpn-service-ur6ef4/deploy/remnawave/ru-node/check.sh
sh check.sh АДРЕС_NL_УЗЛА ИМЯ_ПРИКРЫТИЯ_NL
```

Вывод можно пересылать целиком: секретов в нём нет.

Что смотреть:

- **«общественный белый список: ЕСТЬ»** — у узла есть шанс работать при
  белых списках. Проверяется только телефоном, `docs/18-ru-node.md` §4.2;
- **«НЕТ»** — при белых списках узел работать не будет, но от отрезания
  зарубежных хостингов спасает всё равно;
- **«путь до NL-узла: рукопожатие прошло»** — без этого ставить дальше
  незачем: каскаду некуда выходить.

## 1. Узел

Как в `../node/README.md`, с двумя отличиями:

- 443 здесь **свободен**, вход ставится на него;
- адрес узла в панели — **публичный адрес** RU-машины: панель стоит в
  Нидерландах, а не рядом.

Порт API узла (`NODE_PORT`) открывается **только для адреса панели**:

```bash
ufw allow from АДРЕС_ПАНЕЛИ to any port 2222 proto tcp
ufw allow 443/tcp
ufw allow OpenSSH
ufw enable
```

Открытый всем порт API — это предложение любому подобрать `SECRET_KEY`.

## 2. Служебный пользователь

Через него RU-узел выходит в Нидерланды. Заводится в панели руками:

- **срок** — далёкая дата, **лимит** — без лимита;
- **отряд** — тот, в котором NL-вход;
- **поток** (flow) — `xtls-rprx-vision`, как у NL-входа.

Его `UUID` идёт в `profile.json`, поле `id`. Бот его не трогает: он
работает только с теми, кого завёл сам.

Пользователя видно в панели среди обычных — назовите так, чтобы его не
удалили при чистке: например, `relay-ru`.

## 3. Профиль

Проще всего — собрать на RU-машине сценарием: он берёт выход в NL из
подписки служебного пользователя и сам порождает ключи входа.

```bash
sh make-profile.sh 'ССЫЛКА_ПОДПИСКИ_relay-ru' ИМЯ_ПРИКРЫТИЯ_RU
cat /root/ru-profile.json
```

Руками — `profile.json` как шаблон. Заменить заглушки:

| Заглушка | Откуда |
|---|---|
| `ИМЯ_ПРИКРЫТИЯ_RU` | выбрать по `docs/16-inbounds.md` §3, российское |
| `ЗАКРЫТЫЙ_КЛЮЧ_RU`, `КОРОТКИЙ_ID_RU` | кнопка генерации в редакторе профиля панели |
| `АДРЕС_NL_УЗЛА` | адрес NL-узла |
| `UUID_СЛУЖЕБНОГО_ПОЛЬЗОВАТЕЛЯ` | из шага 2 |
| `ИМЯ_ПРИКРЫТИЯ_NL`, `ОТКРЫТЫЙ_КЛЮЧ_NL`, `КОРОТКИЙ_ID_NL` | из профиля NL-узла в панели |

Заполненный профиль **в репозиторий не возвращается**: в нём ключи и
адреса.

Что в нём устроено так намеренно:

- **российское — напрямую с RU-узла.** Крюк через Нидерланды здесь
  только замедлил бы, а банки и Госуслуги и так ждут российский адрес;
- **частные сети — в `BLOCK`.** Иначе через узел можно было бы
  постучаться во внутреннюю сеть хостера и в API самого узла;
- **торренты — в `BLOCK`.** Жалоба правообладателя придёт российскому
  хостеру, а не нидерландскому, и разбираться с ней будет он.

## 4. Цепочка привязки

Те же четыре шага, что в `docs/16-inbounds.md` §4, — с проверкой
после каждого, а не в конце:

1. **Config Profiles** — вставить профиль;
2. **Nodes → RU-узел → Профили** — включить `RU_ENTRY`; на машине
   `ss -tlnp | grep :443` показывает `LISTEN`;
3. **Hosts** — хост на адрес RU-машины, порт 443, SNI — `ИМЯ_ПРИКРЫТИЯ_RU`,
   шаблон подписки — тот же, что у NL-хоста (иначе на этом пути пропадёт
   раздельная маршрутизация);
4. **Internal Squads** — `RU_ENTRY` в отряд покупателей.

Название хоста — то, что люди увидят в Happ и INCY. Оно должно говорить,
**когда** выбирать этот путь, а не где стоит сервер: например,
«🇷🇺 Если не работает основной».

## 5. Проверить

```bash
# на RU-машине: служебный пользователь доходит до NL
docker logs remnanode --tail 50 | grep -i -E 'TO_NL|error'
```

Затем телефон: Happ → обновить подписку → выбрать RU-хост → открыть
зарубежный сайт. И проверка при ограничениях — `docs/18-ru-node.md` §4.2.
